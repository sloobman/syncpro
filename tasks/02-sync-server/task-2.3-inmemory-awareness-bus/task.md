## 2. Контекст и архитектурная роль
Для комфортной совместной работы пользователи должны видеть курсоры друг друга, текущее выделение текста, имя и аватар коллеги в реальном времени. В отличие от текста документа, информация о курсорах является **эфемерной (ephemeral)**:
- Она не сохраняется в базу данных и S3.
- Она имеет короткое время жизни (TTL $\approx 15-30$ сек).
- При отключении пользователя его курсор должен мгновенно исчезать с экранов остальных участников.

---

## 3. Цели и задачи
1. Реализовать структуру состояния присутствия `AwarenessState`:
   - `client_id`: ID сессии клиента.
   - `user`: объект пользователя (`id`, `name`, `color`, `avatar_url`).
   - `cursor`: позиция (`block_id`, `offset_in_block`).
   - `selection`: диапазон выделения (`anchor`, `head`).
   - `clock`: монотонный счетчик обновления состояния.
   - `last_seen_at`: метка времени последнего обновления.
2. Реализовать in-memory шину Awareness внутри комнаты (`RoomAwarenessBus`):
   - Прием обновлений от клиента с троттлингом.
   - Широковещательная рассылка остальным клиентам комнаты.
3. Реализовать фоновый сборщик "зависших" курсоров (Awareness Sweeper):
   - Проверка клиентов с просроченным TTL каждые 5 секунд.
   - Отправка события `UserLeft` / `CursorRemoved` всем активным участникам при таймауте.
4. Отправка полного снимка Awareness-состояний комнаты новому подключившемуся клиенту.

## 4. Спецификация контракта Awareness

### 4.1. Формат Awareness пакета
```json
{
  "client_id": 42,
  "clock": 17,
  "user": {
    "id": "usr_alice",
    "name": "Alice Smith",
    "color": "#FF5733"
  },
  "cursor": {
    "block_id": "blk_01HXYZ...",
    "offset": 142
  },
  "selection": null
}
```

### 4.2. Механизм инвалидации
- Если от клиента не поступало сообщений в течение `30 секунд`, его состояние помечается удаленным (`null`).
- При штатном отключении WebSocket сокета сервер немедленно транслирует `{ "client_id": 42, "clock": 18, "user": null }`.

---

## 5. Граничные случаи и риски
- Затопление сокета (Flooding) быстрыми движениями мыши: на клиенте и сервере должен быть включен обязательный троттлинг событий (не чаще 1 пакета в 40-50 мс от одного клиента).
- Рассинхронизация часов Awareness: используется счетчик `clock`, обновляемый при каждой мутации, чтобы старое сообщение курсора, пришедшее с сетевой задержкой, не перетерло более свежую позицию.
