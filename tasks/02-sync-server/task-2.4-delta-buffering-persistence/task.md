## 2. Контекст и архитектурная роль
В процессе активного совместного набора текста на сервер поступают сотни посимвольных дельт в секунду. Записывать каждую отдельную дельту напрямую в реляционную БД или объектное хранилище S3 архитектурно недопустимо — это вызовет катастрофическую перегрузку дискового ввода-вывода и истощение пула соединений.

Необходим промежуточный буфер на базе **Redis Streams** с механизмом **дебаунса и пакетной агрегации (batching)**:
- Дельты мгновенно попадают в стрим Redis с низкой задержкой ($<1$ мс).
- Фоновый воркер собирает пачки правок (например, раз в 2 секунды или при накоплении 100 операций).
- Агрегированный батч направляется в контур формирования Merkle-коммитов и записи в S3/Postgres.

## 3. Цели и задачи
1. Реализовать публикатор операций `StreamProducer` в Redis Streams (`XADD`):
   - Ключ потока: `stream:doc:{document_id}`.
   - Поля сообщения: `delta_bytes`, `client_id`, `clock`, `timestamp`.
2. Реализовать механизм консьюмера с Consumer Group (`XREADGROUP` + `XACK`):
   - Гарантия доставки **at-least-once**.
   - Обработка зависших сообщений (`XPENDING` / `XCLAIM`) при аварии воркера.
3. Реализовать дебаунсер (Debounce & Batch Accumulator):
   - Сброс пачки при соблюдении любого из условий:
     - Прошло `T = 2000 мс` с момента последней записи (time-based debounce).
     - Накоплено `N = 100` операций в буфере (size-based flush).
     - Поступил сигнал закрытия комнаты (clean shutdown).
4. Передача агрегированного батча дельт в воркер Merkle-DAG ([TASK-3.1](file:///c:/Users/sloobman/syncpro/tasks/03-merkle-dag-versioning/task-3.1-micro-commits-milestones/task.md)).

## 4. Схема потока данных

```
[WebSocket Room Engine]
       │ XADD delta
       ▼
┌────────────────────────────────────────┐
│      Redis Stream: stream:doc:xyz      │
└────────────────────────────────────────┘
       │ XREADGROUP (Consumer Group: workers)
       ▼
┌────────────────────────────────────────┐
│     Debounce & Batch Accumulator       │
│  - Flush on 2s idle OR 100 ops buffer  │
└────────────────────────────────────────┘
       │ Batch of Deltas
       ▼
┌────────────────────────────────────────┐
│    Merkle-DAG Persistence Pipeline     │
│   (S3 Binary Delta + Postgres Commit)  │
└────────────────────────────────────────┘
       │ XACK (Подтверждение обработки)
       ▼
[Redis Stream Offset Commited]
```

---

## 5. Граничные случаи и риски
- Падение сервера до сброса дебаунс-буфера: благодаря Redis Streams данные не теряются в оперативной памяти процесса, а остаются в стриме Redis до вызова `XACK`. При перезапуске воркер дочитывает необработанные записи.
- Неконтролируемый рост стрима: настройка `MAXLEN ~ 50000` для предотвращения исчерпания RAM в Redis.
