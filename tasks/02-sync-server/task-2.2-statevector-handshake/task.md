## 2. Контекст и архитектурная роль
Когда пользователь открывает документ или восстанавливает соединение после разрыва связи, сервер и клиент должны синхронизировать накопившиеся правки. 
Вместо пересылки всего документа целиком (что недопустимо для 500+ страниц), используется двухфазный дифференциальный протокол на базе **StateVector**.

```
Client                                                 Server (Room In-Memory)
  │                                                               │
  │─────── 1. SyncStep1 (Client StateVector: [A:12, B:5]) ───────>│
  │                                                               │
  │                                    Вычисляет недостающие дельты
  │                                    относительно вектора клиента
  │                                                               │
  │<────── 2. SyncStep2 (Compressed Binary Deltas) ───────────────│
  │<────── 3. SyncStep1 (Server StateVector: [A:20, B:5, C:8]) ───│
  │                                                               │
  │ Вычисляет локальные правки,                                   │
  │ которых еще нет у сервера                                     │
  │                                                               │
  │─────── 4. SyncStep2 (Client Offline Deltas) ─────────────────>│
  │                                                               │
  │ ═══════════════════ СИНХРОНИЗАЦИЯ ЗАВЕРШЕНА ══════════════════│
  │                 (Включение стриминга Update)                  │
```

---

## 3. Цели и задачи
1. Реализовать вычисление разницы дельт по вектору: функция `compute_delta(document, target_state_vector) -> BinaryDelta`.
2. Реализовать обработчик фазы рукопожатия на стороне сервера:
   - Прием `SyncStep1` от клиента.
   - Формирование и отправка `SyncStep2` клиенту.
   - Отправка серверного `SyncStep1`.
   - Прием клиентского `SyncStep2` и применение к документу в RAM.
3. Реализовать переход соединения в статус `READY` для приема и широковещательной рассылки потоковых сообщений `Update`.
4. Гарантировать атомарность: пока идет первичный Handshake, новые входящие `Update` буферизуются в очереди клиента и применяются строго после завершения SyncStep2.

---

## 4. Контракт сообщений
- `MsgType = 0x01` (`SyncStep1`):
  - Полезная нагрузка: Сериализованный `StateVector` (`ClientID -> MaxClock`).
- `MsgType = 0x02` (`SyncStep2`):
  - Полезная нагрузка: Сжатый поток операций вставок, удалений и перемещений блоков.
- `MsgType = 0x03` (`Update`):
  - Единичная правка или короткая пачка операций в реальном времени.

---

## 5. Граничные случаи и риски
- Клиент подключается с абсолютно пустым состоянием (вектор пуст): сервер возвращает полный документ в одном компактном `SyncStep2`.
- Вектор клиента содержит часы больше, чем у сервера (клиент работал офлайн и сделал 500 правок): сервер принимает клиентский `SyncStep2`, накатывает их и рассылает другим участникам комнаты.
- Сетевой обрыв в момент рукопожатия: соединение разрывается, комната не должна зависать в промежуточном заблокированном состоянии.
