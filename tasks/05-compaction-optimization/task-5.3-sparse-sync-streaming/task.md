## 2. Контекст и архитектурная роль
В сверхкрупных документах (книги, энциклопедии, диссертации на 500–1000 страниц) передача всего дерева CRDT при открытии документа перегружает сеть клиента и задерживает интерактивность интерфейса (Time to Interactive).

Для решения этой проблемы применяется протокол **Sparse Sync (Разреженная синхронизация)**:
1. Клиент при подключении загружает только **легковесное дерево структуры документа (Skeleton Tree)**: заголовки разделов, идентификаторы блоков, размеры секций в символах и их хеши (объем данных $\le 20-50$ КБ).
2. Текстовое содержимое секций подгружается асинхронно потоковыми чанками по мере прокрутки документа пользователем или при переходе по ссылке в оглавлении.
3. События реального времени (Live Updates) транслируются клиенту только для тех секций, на которые он явно оформил подписку (`SubscribeSection(section_id)`).

## 3. Цели и задачи
1. Реализовать разбиение документа на независимые секции синхронизации (`SyncPartition`):
   - Раздел верхнего уровня (H1 / Главы) выступает границей партиции.
2. Реализовать сообщение протокола `SyncSkeleton`:
   - Список разделов, количество параграфов, `StateVector` каждого раздела.
3. Реализовать команду запроса секции `RequestSectionData(section_id)`:
   - Сервер формирует бинарную дельту исключительно для запрошенного поддерева.
4. Реализовать фильтрацию Live Updates на стороне шлюза WebSocket:
   - Клиент регистрирует список активных видимых секций `ActiveSubscriptions: Set<SectionID>`.
   - Шлюз фильтрует широковещательные рассылки дельт, отсекая изменения в невидимых клиенту главах.
5. Реализовать prefetching: автоматическая упреждающая загрузка следующей главы при приближении скролла к концу текущей.

## 4. Схема протокола Sparse Sync

```
Client (Browser)                                          Server (Room Sync Engine)
  │                                                                 │
  │─── 1. Connect WS (doc_123) ────────────────────────────────────>│
  │<── 2. Send Skeleton Tree (Headings, BlockIDs, Hashes) [25 KB] ──│
  │                                                                 │
  │ (Пользователь находится в Главе 1)                              │
  │─── 3. SubscribeSection(Chapter_1) ─────────────────────────────>│
  │<── 4. Deliver Section Content & Active Deltas (Chapter 1) ──────│
  │                                                                 │
  │ (Пользователь скроллит к Главе 2)                               │
  │─── 5. SubscribeSection(Chapter_2) ─────────────────────────────>│
  │<── 6. Deliver Section Content (Chapter 2) ──────────────────────│
  │─── 7. UnsubscribeSection(Chapter_1) ───────────────────────────>│
```

## 5. Граничные случаи и риски
- Перемещение блока между разделами (Cross-section Move): если блок перемещен из неподгруженного раздела в активный, сервер должен принудительно доставить данные этого блока вместе с операцией `Move`.
- Полнотекстовый поиск по неподгруженным разделам: поиск выполняется через серверный индекс (PostgreSQL `tsvector` или Elastic/MeiliSearch), который возвращает позицию в документе и команду на подгрузку соответствующей секции.
